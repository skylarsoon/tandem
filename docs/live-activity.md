# Live planning activity

The conversation and discussion views share a **Behind the plan** panel. Its summary stays outside transcript scrolling. Expand it to see Apify searches, provider/actor/run references, usable result counts, agent status, planning stages, and a timestamped activity history. It follows room subscriptions and never starts searches from the browser.

`RESEARCH_ACTIVITY` events come from the worker's actual Apify gateway transitions: queued, starting, running (provider status checks), collecting, completed, cached, or failed. A request-scoped observer binds them to the current job, generation, attempt, round, and input/membership/permission revisions through the existing lease-checked event reducer. The room research router's dynamically created gateways inherit the observer. A strict projection of the submitted actor input exposes routes, travel dates, locations, shared restaurant queries, traveller counts and collection limits. Full actor inputs, owner identities, private budget/stop/bag filters, dataset contents, private reasons, prompts, provider exception text, and credentials are excluded. If the database flags any projected text as private, the worker retries only the telemetry without that context. Recognized failures are translated into fixed user-facing messages.

Recent dataset reuse is labeled explicitly and does not start a new actor. A usable result count is a normalizer output count, not a claim that all options satisfy the group. Poll-deadline failure means the worker stopped monitoring; it does not claim the remote actor was cancelled. Queues are distinct from running searches. Disconnects, superseded attempts, stopped workflows, and updates older than 45 seconds never display as active work. No progress percentage or completion ETA is invented. Earlier inputs/jobs remain available in history.

Existing workflow and agent activity records supply planning and conversational progress. If there are no execution events, the UI says so rather than claiming a worker is busy. This is an activity record, not a global service-uptime monitor. Long model calls without new events will appear as awaiting updates. Historical actor runs from before this feature cannot be reconstructed from local logs in the UI.

## Search context and conversational presentation — November 1, 2026
Each new run reports the criteria actually sent to its actor. Older runs explicitly say their search details were not reported; the UI never reconstructs an old query from today's trip settings. Completed collection reports usable, excluded and duplicate counts, plus whether the collection limit was reached. These are not approval counts and do not imply exhaustive search.

Shared discussion follows incoming messages with an opt-out for reading history, timestamps, addressed recipients and active-speaker/new-update cues. Scrolling away or choosing Pause following prevents new arrivals from pulling the reader back. Reduced motion is respected. Audio remains opt-in and stops on private/shared boundaries. Mediator and personal-agent wording is generated by Claude from the actual typed negotiation act and room-safe, cited candidate facts. Recent published turns provide context, never new evidence. Reference/numeric checks and an independent semantic review precede publication; failed reviews produce an explicitly labelled verified fallback. Private profiles, caps and reasons never enter this wording stage. This review is defense in depth, not a guarantee against every model error. The frontend displays and speaks the published utterance verbatim; it only deduplicates redelivery of the same message ID. Wording never changes optimizer decisions, permission checks, research triggers or human approval. Both model calls use existing budgets and operation receipts. Existing transcript records are not rewritten.

Validation: 416 worker unit tests and 105 frontend tests pass, including private-field exclusion, telemetry fallback, search-context rendering and grounded distinct turns. Browser tests cover new arrivals, follow-live control, voice privacy and exact plan consent.

## Conversations throughout full-trip planning

Pips represent travellers in the actual worker workflow. A completed provider search can now publish a `RESEARCH_UPDATE` handoff before the full research batch finishes. These messages cite recorded observations and explicitly distinguish research from eligibility, selection and approval. Outbound and return one-way observations cannot enter the itinerary solver: their references are prefixed `research-only:`. Full result reuse requires a completed research batch for the same input and membership revisions; permission-only updates do not invalidate search observations. The optimizer, individual agent decisions, permission gates and human reviews still determine the plan.

The service has separate bounded conversation and planning lanes. Private questions can be processed while one plan is researching or negotiating. In Agent discussion, **Talk to your Pip** opens an owner-only conversation without switching away from the group. Status answers use the current planning job and its reported activity, not a previous failed attempt; other travellers' private facts are excluded. No artificial conversation timer, invented typing transcript or fabricated disagreement is used. A turn appears after its generation and validation complete.

Utterance validation receives preceding published turns as conversational context, never as a substitute for evidence. A rejected draft receives its failed checks on the repair attempt. Unsuccessful repairs remain clearly labelled fallbacks. Typed source facts include flight connections and return dates, and activity/dinner prices remain explicitly per-person planning estimates rather than final quotes.

Organizers can request a retry after a recognized recoverable provider failure. The reducer rejects active-job duplicates, non-organizers, successful jobs and ambiguous paid starts. Budget-stopped jobs may be retried after a UTC reset or operator-approved increase, but every provider call still checks the durable budget. The UI immediately shows the accepted retry as queued. Each actor's polling deadline begins when its concurrency slot opens; waiting in the local queue does not consume that deadline. Daily provider limits are unchanged.

Ordered trip stages are shown before brief confirmation and in the trip overview. Later activity, dinner and transfer searches retain the confirmed destination context even when no new flight search is needed. Research covers the full requested trip, and later stages continue to use the worker's existing allocation and negotiation logic.

A live two-traveller diagnostic returned all seven flight/stay/activity/dinner searches and reached a real private concession question; a fresh full-stage recording is being verified separately. An isolated real-Claude wording check passed both generated/reviewed turns in four calls. Test fixtures and isolated evaluations are not presented as live trip results.

## Date-scoped operator allowances

The default service limits remain 500 Claude calls and 40 Apify starts per UTC day. `ProviderBudget.set_daily_limit` records an explicitly authorized ceiling for one exact UTC date and service scope. It does not reset usage, alter per-run charge limits, or carry the override into the next day. The reservation transaction and status report read the same effective ceiling. A November 1 walkthrough allowance of 44 Apify starts was approved separately; this is runtime operator state, not a new default.
